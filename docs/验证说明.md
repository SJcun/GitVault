## 自动化验证

使用真实 Git 仓库，覆盖下列场景：

1. 电脑 A 导入 → B 克隆 → A 推送 → B 拉取 → B 推送 → A 拉取，最终提交 OID 和文件一致。
2. 不改变已有 origin、usb 和 upstream；未提交文件不会被传输。
3. 两边分叉时拒绝普通推送和快进拉取，不改写任一端提交。
4. 工作区有修改时禁止拉取，文件内容和本地 HEAD 保持不变。
5. 新建同名分支、删除远端分支后的缓存清理，用户 push.followTags 配置不会导致意外推标签。
6. Vault 改路径后身份不变；原位置被不同 Vault 替换时拒绝传输。
7. 无共同历史的项目拒绝绑定。
8. 空仓库、Detached HEAD、未完成合并及浅克隆具有明确的不支持状态。
9. 当前提交的 LFS 属性和子模块被识别，不显示为完整迁移成功。
10. 接收端 hook 拒绝推送时返回真实错误，远端 HEAD 不变。
11. 导入或克隆不覆盖已有目录。
12. 未登记裸仓库可恢复，重复恢复不产生重复项。
13. 清单只读造成实际登记失败后，源项目和完整裸仓库保留，可恢复登记。
14. 首次导入保留本地分支和标签，后续推送只更新当前分支。
15. 清单路径穿越、缺失字段与损坏设置不能静默接受或覆盖。
16. 远端缺失时刷新失败；运行中的 Git 能被取消并终止。

## U 盘格式兼容性（FAT32 / exFAT）

在实际 FAT32 U 盘（盘符 K:，卷标 `U盘_孙`）上复现并修复了一处传输阻塞：

- 现象：`git -C <U盘裸仓库> rev-parse --is-bare-repository` 退出码 128，报 `detected dubious ownership` 与 `is on a file system that does not record ownership`。克隆步骤本身已成功，失败发生在紧随其后的裸仓库校验。
- 原因：FAT32 / exFAT 不记录文件属主，git 2.35.2 起将「读不到属主」一律判为可疑所有权。
- 修复：`GitCommandService` 在每次调用时注入 `safe.directory`，不写入用户全局 Git 配置。
- 关键细节：必须经**环境变量**（`GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_n` / `GIT_CONFIG_VALUE_n`）注入，不能用命令行 `-c`。git 把 `-c` 转成 `GIT_CONFIG_COUNT` 传给对端子进程时会过滤 `safe.directory`，因此 `push`/`fetch` 派生的 `receive-pack`、`upload-pack` 仍会按可疑所有权拒绝 FAT32 上的裸仓库；环境变量则由子进程原样继承。
- 验证范围：在该 U 盘上直接启动 `receive-pack` 对比三种情形——无 `safe.directory` 时报 `detected dubious ownership`；经环境变量传入 `*` 或该仓库具体路径时均通过所有权检查并进入协议协商。命令行 `-c` 场景则由修复前的实际 push 报错确认失效。完整 `ImportAsync` 未能在本次会话内跑通，原因是会话沙箱禁止 git 的 `sh.exe` 创建命名管道（`couldn't create signal pipe, Win32 error 5`），与本次修复无关。
- 局限：同一文件系统上手工写入具体路径的 `safe.directory` 条目（git 报错提示的建议）无效，只有 `*` 有效；此结论由实测确认。

自动化测试仍运行在 NTFS 临时目录，无法复现「文件系统不记录属主」这一条件，因此该项依赖上述真实 U 盘人工验证。

17. 绑定已有项目时选中代码库根目录、其中的裸仓库或非仓库目录，都给出可执行的说明而不是 Git 原始报错。

18. `safe.directory` 经环境变量传给子进程的契约（批处理探针断言 `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_n` / `GIT_CONFIG_VALUE_n`）。
