# GitVault V1 实施方案

日期：2026-09-21。状态：方案草案，本轮不实现程序。

## 1. 目标与设计前提

把 U 盘上的裸 Git 仓库作为离线中转站，让不同电脑方便地加入项目、克隆、推送和拉取，避免反复输入路径和命令。代码和仓库信息不依赖第三方平台。

以原“U盘 Git 工具设计”讨论为需求依据，按本次要求使用 **.NET 8**。原讨论中可读取的内容包含功能和文本布局建议，没有完整的最终界面稿。

本方案采用以下默认假设，属于建议而非已经确认的额外需求：

- 首版面向 Windows x64，使用中文桌面界面。
- 用户已经使用 Git 管理项目；提交代码继续在 IDE 或其他 Git 工具中完成。
- 首版使用本机 Git；可以指定便携版 git.exe 路径，但不自动下载或捆绑 Git。
- 一个 Vault 可以保存多个仓库；每台电脑为每个仓库绑定一个本地工作目录。
- 首版支持普通、完整的 Git 仓库；不承诺迁移 Git LFS 内容、子模块仓库及浅克隆缺失的历史。

“便携”有两种含义：U 盘携带仓库，或 U 盘同时携带程序、运行时和 Git。本方案先保证前者，程序提供自包含压缩包；完整捆绑 Git 的版本后续再评估。

## 2. 首版范围

| 功能 | 具体行为 |
| --- | --- |
| 创建 / 打开 Vault | 选择 U 盘目录，创建标识文件；也支持手动打开已有 Vault |
| 本地项目加入 U 盘 | 创建裸仓库，记录本机绑定 |
| U 盘仓库克隆到本机 | 选择目标目录，克隆成功后自动绑定 |
| 绑定已有本地项目 | 检查仓库与历史关系，避免重复克隆 |
| 查看状态 | 显示当前分支、本地领先数、U 盘领先数、工作区修改、刷新时间 |
| 推送到 U 盘 | 只推送当前分支，允许显式创建 U 盘端同名分支 |
| 从 U 盘拉取 | 仅快进更新，不自动生成合并提交 |
| 最近提交 | 展示当前分支最近 20 条提交的短哈希、标题、作者、时间 |
| 操作反馈 | 显示进度、结果、可复制的 Git 错误与操作日志 |

首版不包含：暂存/提交、分支管理、自动合并或 rebase、冲突编辑器、强制推送、删除远端分支、批量同步、云平台集成、账号、自动备份、代码 Diff 编辑器。

原讨论提出过“拉取并合并”。建议首版收窄为“检测分叉并打开本地目录”，用户通过现有工具解决后回来刷新，避免为小工具引入完整的冲突处理流程。

## 3. 技术选型

| 项目 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | .NET 8，目标 net8.0-windows | 遵循本次要求 |
| 桌面 UI | WPF + MVVM | 适合 Windows 文件与进程操作 |
| MVVM | CommunityToolkit.Mvvm | 减少属性通知和异步命令样板代码 |
| Git | 调用 Git CLI | 直接使用 Git 行为，方便诊断 |
| 配置 | System.Text.Json + JSON 文件 | 数据量小，无需数据库 |
| 测试 | xUnit + 临时真实 Git 仓库 | 验证实际分支和数据变化 |
| 发布 | win-x64，自包含文件夹压缩包 | 目标电脑无需另装 .NET 运行时 |

不引入 WebView、服务端、插件框架、通用仓储层或复杂依赖注入框架。UI 先使用 WPF 控件和少量资源样式。

发布时显式设置 SelfContained=true，不把指定 win-x64 等同于自包含。首版不追求单文件、裁剪或 Native AOT。[.NET 8 发布行为说明](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/8.0/runtimespecific-app-default)

按当前官方支持周期，.NET 8 将于 2026-11-10 结束支持。本方案仍按 .NET 8 实施；后续框架升级独立决策，不在本次擅自改为 .NET 10。[官方支持政策](https://dotnet.microsoft.com/en-us/platform/support/policy)

## 4. 界面方案

主窗口采用左侧仓库列表、右侧详情、底部操作反馈。默认浅色界面，状态同时使用文字和图标，不只依赖颜色。

```text
GitVault                         [打开 Vault] [新建 Vault] [设置]
我的代码库 · F:\GitVault         已连接              [刷新]
────────────────────────────────────────────────────────────────
仓库                  │ MyTool
[搜索仓库]            │ 本地：D:\Projects\MyTool       [打开目录]
[加入本地项目]        │ U 盘：F:\GitVault\repos\MyTool.git
                      │
● MyTool              │ 当前分支：main
  main · ↑ 3          │ 本地领先 3 次提交 · U 盘领先 0 次提交
                      │ 工作区干净 · 刚刚刷新
● AgentPlatform       │
  main · ↓ 2          │ [推送到 U 盘]  [从 U 盘拉取]
                      │
⚠ TestProject         │ 最近提交
  main · 已分叉       │ a8321fe  修复状态刷新       今天 10:30
                      │ d32f210  增加日志           昨天 18:20
○ AnotherTool         │
  本机未绑定          │
────────────────────────────────────────────────────────────────
上次操作：推送成功                         [展开操作日志]
```

关键页面状态：

- 无 Vault：提供“创建 Vault”和“打开已有 Vault”。
- 未绑定：详情区提供“克隆到本机”和“绑定已有项目”。
- 已分叉：显示两侧提交数，禁用普通推送和拉取，说明需要先在其他 Git 工具处理。
- 工作区有修改：单独标注；允许推送已提交内容，禁用拉取，不自动 stash。
- U 盘离线：保留列表与上次状态，但标为“离线 / 数据已过期”，禁用传输。
- 操作中：显示阶段和 Git 进度，同一仓库禁止重复操作；可取消，但取消后的状态必须重新检查。

对话框仅保留创建 Vault、加入项目、克隆/绑定、设置。设置首版只有 Git 路径等必需项。

## 5. 数据与盘符变化

U 盘建议结构：

```text
GitVault/
  vault.json
  repos/
    MyTool.git/
    AgentPlatform.git/
```

vault.json 保存 schemaVersion、稳定的 vaultId、显示名称，以及仓库列表。每项包含 repoId、显示名称、相对路径；不保存本机工作目录或固定盘符。

本机 %LocalAppData%\GitVault\settings.json 保存 Git 路径、最近打开的 Vault 位置，以及 (vaultId, repoId) 到 localPath 的绑定。操作日志也保存在本机，避免频繁写 U 盘。

识别策略：

1. 启动、设备变化和手动刷新时检查已知位置及移动盘根目录下的 GitVault\vault.json，不递归扫描整块磁盘。
2. 自定义路径和被系统识别为固定盘的移动硬盘允许手动打开；找到后记住位置。
3. 用 vaultId 识别身份，执行前重新验证标识和仓库路径，不能只认盘符。
4. 同时出现两个相同 vaultId 的位置时要求选择，不自动选第一个。
5. 仓库相对路径解析后必须位于当前 Vault 的 repos 目录内。

首版目录名称创建后保持不变，显示名称可与目录名称分离。配置通过同目录临时文件替换方式保存；解析失败不覆盖原文件。

## 6. Git 操作设计

### 6.1 remote 方案选择

有两种实现：维护名为 usb 的 remote，并在盘符变化后修改 URL；或每次直接使用已识别的绝对路径。

选择第二种，避免覆盖已有 usb / origin、改变原有 upstream。应用获取分支数据时写入专属引用空间 refs/gitvault/<vaultId>/<repoId>/heads/*，不与常规 remote-tracking refs 混用。

从 U 盘克隆时，Git 会创建带路径的 origin；工具在自己新建的克隆中移除该临时 origin，随后由专属引用机制管理。界面和说明中明确：U 盘同步通过 GitVault 执行，普通 git pull 不会自动找到 U 盘；用户可自行配置其他 remote。

### 6.2 本地项目加入 U 盘

1. 检查本地目录是普通、非浅克隆的工作仓库，至少有一个提交且 HEAD 在分支上。
2. 显示待导入项目、目标目录和“仅包含已提交内容”。
3. 在 U 盘唯一临时目录执行 git clone --bare --no-hardlinks，将本地分支和标签复制过去，不额外执行重复 push。
4. 验证裸仓库和默认分支；成功后改为最终目录，再登记清单和本机绑定。
5. 目标已存在时不覆盖。失败时保留可识别的临时目录并提供重试/清理提示；只处理本次创建的目录。

--bare 不产生工作区；--no-hardlinks 避免文件硬链接依赖。它不是完整镜像全部引用的 --mirror，也不会收录未提交内容。[git clone 文档](https://git-scm.com/docs/git-clone)

### 6.3 克隆和绑定

- 克隆先写入目标父目录下的唯一临时目录，成功后移至用户选定的最终名称，再写绑定。
- 默认目标必须不存在；既有项目走“绑定已有项目”。
- 绑定时抓取 U 盘引用，检查当前同名分支的共同历史；没有共同历史则拒绝自动关联。U 盘尚无该分支时，让用户选择具有共同历史的已有本地分支完成绑定。
- 分支切换通过用户现有工具完成，回到窗口时重新读取当前分支。

### 6.4 状态刷新

先读取 HEAD、分支、工作区和是否存在未完成的 merge/rebase，再执行定向 fetch：

```text
git -C <local> fetch --no-tags --prune <vaultRepoPath> +refs/heads/*:refs/gitvault/<vaultId>/<repoId>/heads/*
git -C <local> rev-list --left-right --count HEAD...<对应的U盘分支引用>
```

左侧计数是本地独有提交，右侧是 U 盘独有提交。fetch 的 + 仅允许更新本机缓存引用，不是强制推送；prune 仅针对该映射清理过期缓存。[git fetch](https://git-scm.com/docs/git-fetch)、[git rev-list](https://git-scm.com/docs/git-rev-list)

| 本地独有 | U 盘独有 | 展示与操作 |
| --- | --- | --- |
| 0 | 0 | 当前分支已同步 |
| >0 | 0 | 可推送 |
| 0 | >0 | 工作区干净时可快进拉取 |
| >0 | >0 | 已分叉；交给外部工具处理 |
| U 盘无同名分支 | — | 显示“在 U 盘创建此分支”，用户主动执行 |
| 无共同历史 | — | 显示历史不相关，禁止自动同步 |
| fetch 失败 | — | 未知 / 刷新失败，不能显示为已同步 |

标签只在初次加入/克隆时按 Git 的克隆行为带入；后续按钮仅同步当前分支，不承诺标签同步。列表中的状态必须注明分支，不能把单分支一致说成整个仓库一致。

### 6.5 推送和拉取

推送前重新读取状态，普通推送明确使用 refs/heads/<branch>:refs/heads/<branch>，不使用 --force、--mirror 或 --all。推送完成再刷新；若期间另一进程改变远端，交给 Git 拒绝非快进更新并展示原因。

拉取采用“fetch → 检查 → git merge --ff-only <已抓取的提交OID>”。使用已检查的提交 OID，执行前复核当前分支与 HEAD 未变；工作区必须干净且无未完成操作。Git 拒绝快进时保留现场，不自动重置或合并。[git merge 文档](https://git-scm.com/docs/git-merge)

Detached HEAD、未创建首次提交、浅克隆和正在解决冲突的仓库提供明确说明，禁用同步按钮。检测到 LFS 或子模块时说明额外内容不在首版保障范围，不能声称已完成完整离线迁移。

## 7. 代码结构与执行约束

```text
GitVault.sln
src/
  GitVault.App/              WPF 视图、ViewModel、样式和应用入口
  GitVault.Core/             数据模型、Git 执行、Vault 与同步流程
tests/
  GitVault.Core.Tests/       临时真实仓库的集成测试和必要单元测试
docs/
  GitVault-V1-方案.md
```

Core 保持少量具体服务：GitCommandService 负责启动和读取进程；VaultService 负责发现及清单；RepositoryService 负责同步流程和状态；SettingsService 负责本机配置。只在确有测试替换需求时引入接口。

- 使用 ProcessStartInfo.ArgumentList 传递参数，不拼接 shell 命令；中文、空格和特殊字符路径纳入测试。
- 异步读取标准输出与错误流，退出码决定成功与否，不能把 stderr 有内容直接视为失败。
- Git 操作不阻塞 UI，首版使用简单串行任务队列，避免同时竞争 U 盘。
- 禁止终端交互提示；需要用户处理的错误回到界面，不让隐藏进程无限等待。
- 取消时终止相关进程树并标为“已取消，需复核”，不能假设已经回滚。
- 不主动访问网络；发现外部过滤器/钩子导致额外依赖时显示实际错误，不静默下载。
- 新代码对类、函数、字段和关键逻辑写清中文注释，匹配用户的工程约定。

## 8. 故障处理

| 情况 | 预期行为 |
| --- | --- |
| 未找到 Git | 提示安装 Git 或选择 git.exe，不创建仓库 |
| U 盘只读 / 空间不足 | 停止写入并展示具体失败；保留源仓库 |
| 中途拔盘 | 终止当前流程，状态变为离线/待检查；重连后重新抓取验证 |
| Git 锁文件存在 | 报告仓库忙或需人工检查，不自动删除锁文件 |
| 清单未写入但仓库已创建 | 重开时识别未登记的裸仓库，提供恢复登记，不覆盖仓库 |
| 清单记录的仓库缺失 | 标记缺失，不自动重建或悄悄删除记录 |
| 操作结果不确定 | 重新读取引用确认实际结果，必要时提示人工运行 git fsck |

Git 的引用更新不等于对突然断电或文件系统损坏的绝对保护。首版提供可诊断的失败处理，不承诺断电自动修复，也不把 U 盘中转等同于独立备份。

## 9. 实施步骤与验收

1. **工程与 Git 基础层**：建立 .NET 8 工程、Git 探测、异步进程封装和结果模型。验收：中文/空格路径可用，错误与取消可返回，窗口不阻塞。
2. **Vault 与完整传输闭环**：创建 Vault、加入项目、克隆、绑定、状态计算、推送、快进拉取。验收：临时目录模拟电脑 A、电脑 B 和 U 盘，完成 A 提交 → 推送 → B 拉取 → B 提交 → A 拉取，文件和提交 OID 一致。
3. **主界面与设备发现**：实现列表、详情、对话框、状态按钮和日志。验收：未绑定、领先、落后、分叉、离线等状态能清楚展示，按钮符合规则。
4. **异常验证与发布**：验证中断、路径变化、失败恢复，生成自包含包与简短使用说明。验收：未安装 .NET 运行时但已安装 Git 的 Windows x64 环境可运行，真实 U 盘换盘符后仍能定位正确仓库。

必须覆盖的自动化场景：

- 已同步、单边领先、双边分叉、同名分支缺失、远端分支删除后的缓存清理。
- 保留已有 origin、usb 和 upstream；不会推送到错误仓库。
- 工作区有修改时禁止拉取，推送不包含未提交文件。
- 推送被拒绝、Git 返回非零状态时不标记成功。
- 新增/克隆失败不覆盖既有目录；清单失败后可恢复登记。
- 本地无提交、Detached HEAD、浅克隆和无共同历史有明确状态。

真实硬件人工验证补充：换盘符、只读 U 盘、磁盘写满、中途拔出与重新插入。自动测试不冒充真实硬件断电测试。

最终交付：源码、测试、自包含 Windows x64 压缩包、使用说明。成功标准是两台电脑能在无第三方 Git 平台的情况下，通过同一 U 盘完成可理解、可验证的双向提交传输。
